# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Single-page marketing/engagement site for **Peace Academy of West Texas (PAWTX)**, a nonprofit in Odessa/Midland, TX. React 19 + Vite 6 + TypeScript + Tailwind CSS v4, with a **Supabase backend** (Postgres + Auth + Storage + Edge Functions) and **Stripe Checkout** for donations. Scaffolded from Google AI Studio (see `metadata.json`, `README.md`).

## Commands

```bash
npm install        # Node >= 18 required (Vite 6)
npm run dev        # dev server on http://localhost:3000 (host 0.0.0.0)
npm run build      # production build to dist/
npm run preview    # serve the built dist/
npm run lint       # tsc --noEmit — TYPE CHECK ONLY, the sole automated gate
npm run seo:assets # regenerate public/og-image.jpg and the favicons
npm run seed:legal # regenerate the legal seed migration from legal/*.md
npm run setup:bundle # regenerate supabase/setup/00_full_setup.sql from the migrations
npm run setup:check  # verify supabase/setup/ still agrees with supabase/migrations/

npm run db:start   # local Supabase stack (needs Docker Desktop running)
npm run db:stop    # stop it
npm run db:reset   # re-run migrations + supabase/seed.sql
npm run db:push    # apply migrations to the linked remote project
npm run db:types   # regenerate src/lib/database.types.ts from the live schema
npm run functions:serve   # Edge Functions locally
npm run functions:deploy  # deploy all seven (stripe-webhook gets --no-verify-jwt)
```

There is **no test framework** — `npm run lint` is the only automated check. The
one exception is `supabase/tests/`, three hand-run scripts covering prepaid
event tickets (the database lifecycle, `create-ticket-session`, and
`stripe-webhook` driven with properly signed synthetic events). They are not in
CI and nothing else has an equivalent; they exist because that is the only code
here that moves money attached to a particular seat on a particular date, and
`tsc` cannot tell you whether the seat comes back when a payment fails. See
`supabase/tests/README.md`, and run them after touching the ticket migration or
any of those three functions. Run it before considering any change done. Note that `tsconfig.json` does **not** enable `strict`; in particular `strictNullChecks` is off, so TypeScript will not narrow a union by a boolean discriminant (this is why `ActionResult`'s success branch declares `error?: undefined`). `tsconfig.json` excludes `supabase/` because Edge Functions are Deno modules that import from `https://` URLs.

## Deployment

Pushing to `main` triggers `.github/workflows/deploy.yml`, which runs `npm run build` and publishes `dist/` to GitHub Pages. The site is served from the custom domain in `public/CNAME` — **pawtx.org** — so it now sits at the root of its own origin: `SITE_PATH` in `src/lib/seo.ts` is `/`, and `vite.config.ts` takes the build `base` from it (dev and preview are `/` too). The earlier `new.pawtx.org` and `erohaj.github.io/peace-academy-of-west-texas/` addresses both redirect there, so nothing already shared breaks. The DNS for this lives in **Wix**, which still holds the domain's nameservers — and the Resend DKIM/CNAME records for `mail.pawtx.org` sit in that same zone, so moving the nameservers off Wix silently kills transactional email. Do not hardcode either path in app code; use relative asset imports/`import.meta.env.BASE_URL` if an absolute base path is ever needed — a sub-path is one `SITE_PATH` edit away from coming back.

## Architecture

**No router.** The whole app is state-driven from one Zustand store; the backend is Supabase, called directly from the browser.

- **Navigation** is a single `activeTab` field (`'home' | 'events' | 'social' | 'gallery' | 'donate' | 'volunteer' | 'admin'`) in `src/store/useAppStore.ts`. `App.tsx` conditionally renders sections from it — `home` stacks several sections; other tabs render one. To add a "page": extend the `ActiveTab` type in `src/types/index.ts` and add a branch in `App.tsx`. Nav lives in `Navbar`/`Footer`, which call `setActiveTab`.

- **Backend layout.** `supabase/migrations/` holds the schema (`*_init_schema.sql`), the RLS policies and the `create_rsvp` function (`*_rls_and_rpc.sql`), and the Storage bucket (`*_storage.sql`). `supabase/seed.sql` carries the former `mockData.ts` content. `supabase/functions/` holds seven Deno Edge Functions: `create-checkout-session`, `create-ticket-session`, `stripe-webhook`, `donation-status`, `ticket-status`, `send-contact-message`, `send-rsvp-confirmation`. `supabase/setup/` is the path for someone without the CLI, who pastes SQL into the dashboard editor. `00_full_setup.sql` is **generated** — `npm run setup:bundle` (`scripts/generate-setup-bundle.mjs`) concatenates every migration in filename order plus `seed.sql` — so never hand-edit it; `supabase/migrations/` is the source of truth. It was assembled by hand until it had silently fallen eleven migrations behind, installing a 26 July schema with no error to say so. The other three files there — `97_check_auth`/`98_verify`/`99_reset` — are **not** generated and cannot be: they assert what the schema should mean (which tables carry PII and must have no `anon` policy, that only `revoked_at`/`revoked_reason` stay writable on an issued certificate, that `create_rsvp` exists once with eight arguments, that the ticket payment functions are not callable by `anon`) and drop a table list. Adding a migration means editing them by hand, and `99_reset` forgetting a table leaves a half-cleaned database that fails the next install on "already exists". `npm run setup:check` (`scripts/check-setup-helpers.mjs`) is what catches that: it parses the migrations with libpg_query — Postgres's own parser as a library — and compares what they create against what those two files name, plus asserts the bundle on disk matches what the generator would produce. Note it can only compare names and counts; it executes nothing, so an incorrect `USING` clause or a bad ordering between migrations still needs the local stack.

- **RLS is the only security boundary.** The site is a static bundle on GitHub Pages, so the anon key ships to every visitor and the browser talks to PostgREST directly. Anything not explicitly denied by a policy is public. `rsvps`, `donations` and `contact_messages` have **no** public `select`; `events`, `gallery_items` and `shifts` are readable when `published`. Writes to content tables require `profiles.role = 'admin'`, checked via the `is_admin()` SECURITY DEFINER helper (a policy on `profiles` that queried `profiles` directly would recurse). Column privileges — not policies — are what stop a user setting their own `role`, and what stop an admin clobbering `events.reserved_spots`.

- **State** lives in `useAppStore`, which holds both the raw database rows (`raw.events`, `raw.shifts`, …) and the mapped view models. Display labels are language-dependent, so `setLanguage` re-runs `derive()` over the stored rows rather than refetching. `initialize()` loads content and subscribes to auth; it is guarded by a module-level flag against StrictMode's double effect.

- **Data access** is `src/lib/api/*` — one module per table, mapping snake_case rows to the camelCase types in `src/types/index.ts`. Actions return `ActionResult` (`{ok:true}` / `{ok:false, error}`) rather than a bare boolean, so the UI can distinguish "event full" from "already registered" from a network failure. `src/lib/api/errors.ts` maps the custom SQLSTATEs (`PA001`–`PA006`) raised by `create_rsvp` onto those codes.

- **Volunteer hours are a ledger, not a calculation.** `service_log` holds credited hours and every row was written by an admin closing a shift's roster (`ShiftRoster.tsx` → `closeRoster()`); volunteers have no insert or update policy on it. `shift_signups.attendance` is the separate record of what staff observed, and `null` there is what marks a roster as still needing to be closed. Hours used to be summed in the browser from claimed shifts whose end time had passed, which credited people who never turned up — do not reintroduce that, the service letters this feeds are handed to schools and courts. `fetchMyServiceLog` deliberately survives the table being absent (a deploy can outrun the migration) but only that error; anything else throws rather than reporting zero hours to someone who served fifty.

- **Volunteer paperwork is versioned and hashed, on purpose.** `legal/*.md` is the source an attorney reviews; `scripts/generate-legal-seed.mjs` derives `supabase/migrations/*_seed_legal_documents.sql` from it — never hand-edit the seed migration or it drifts from the drafts. Each `legal_document_versions` row carries a `body_hash` (trigger-computed), and `document_signatures` copies that hash rather than joining it at read time, so a signature stays provable even if the document text is later corrected. Signatures cannot be updated or deleted, admins included. `OnboardingWizard.tsx` treats the `application` kind specially — it renders a real form (`ApplicationForm`), not a read-and-sign step; the other five kinds render via `MarkdownDocument`, whose blockquote renderer gives a `> ### heading` blockquote (currently only the express-negligence paragraph in the release) a bold boxed treatment — that structural marker, not content-sniffing, is what satisfies Texas's conspicuousness requirement (Dresser Industries v. Page Petroleum), so don't remove the heading from that one blockquote without keeping the visual weight some other way. See `legal/README.md` before changing any of the six documents; none of them should reach a real volunteer before a Texas-licensed attorney has reviewed them.

- **A signature stays readable even after its document is revised.** `document_versions: read own signed` lets a non-admin read a specific `legal_document_versions` row if they have a `document_signatures` row pointing at it — additive to `read current`, so it only ever widens access to a version *this* user actually signed. Without it, publishing a new version of a document would retroactively block every prior signer from viewing (or printing, via `SignedDocumentView.tsx`) the exact text they agreed to, even though the hash still proves what it was. `SignedDocumentView` is shared between `ApplicationsAdmin` (staff reviewing an application) and the volunteer's own "Volunteer Forms" tab once complete — same component, because what is provable does not depend on who is looking.

- **Certificates read a ledger, not a query.** `CertificatesAdmin` snapshots `service_log` entries into `volunteer_certificates.entries` at issue time; `verify_certificate()` is a SECURITY DEFINER RPC, not a table policy, so anonymous verification can never widen into a listing of every certificate or leak the PII on `volunteer_applications`. Revoke, don't delete, a certificate issued in error — `CertificateVerify.tsx` reports "withdrawn" with the date, since "no such certificate" reads as a forgery to whoever is holding a printed copy.

- **RSVP capacity** is enforced by `create_rsvp()`, which takes a `FOR UPDATE` lock on the event row. Direct inserts into `rsvps` are revoked from anon and authenticated — the RPC is the only way in. Never re-add a client-side seat check; two simultaneous submissions cannot see each other's pending writes. The same RPC also refuses an event that is over (`coalesce(ends_at, starts_at) <= now()`, PA006) — `ends_at` is nullable and an event still running stays bookable. `fetchEvents` hides those events from the public feed with the identical rule, but that filter is only the courtesy: it is a snapshot taken at fetch time, and the RPC is what actually holds when a page has been left open past the end of the event.

- **A prepaid seat is held before it is paid for, and `reserved_spots` counts the hold.** On an event with `payment_required`, `create_rsvp` writes the booking as `payment_status = 'pending'` with a `hold_expires_at` 35 minutes out and counts its seats immediately — a seat somebody is paying for this minute is not available to anyone else. The hold comes back by one of four paths: `release_expired_rsvp_holds(event_id)`, which `create_rsvp` itself calls under the event's own lock before every capacity check (so no visitor is ever turned away by an abandoned cart, and there is no cron job to depend on); `release_rsvp_hold` from the webhook's `checkout.session.expired`; or `mark_rsvp_refunded` from `charge.refunded`. Stripe's session is set to expire two minutes *before* the hold, so a payment can never land on a seat already given away — and `mark_rsvp_paid` still re-takes the seats if one does, going over capacity with a logged warning rather than charging somebody for a place they cannot have. **Every one of them takes the event row's lock before touching a booking** — that order is the schema's rule, because `create_rsvp` locks the event first and a function that went the other way round would deadlock against somebody booking the same event at the moment a payment lands, which is exactly when these run. A full `release_expired_rsvp_holds(null)` sweep is therefore a loop of per-event calls rather than one set-based UPDATE. Those four functions are the only writers of `reserved_spots` besides `create_rsvp`, EXECUTE on all of them is revoked from `anon` and `authenticated` (`revoke ... from public` as well as the two roles — a new function is granted to PUBLIC by default, and revoking from the roles alone leaves that standing), and `98_verify.sql` asserts it.

- **Payments.** The donation form has **no card field, deliberately** — collecting a card number in the page would put the site in PCI scope. `createCheckoutSession` calls an Edge Function that validates the amount server-side and returns a hosted Stripe URL; the browser navigates there. Stripe returns to `?donation=success&session_id=…`, which `App.tsx` reads (no router) and routes to the donate tab. The `stripe-webhook` function is the only writer that marks a donation `paid`, and it must be deployed with `--no-verify-jwt`. Donation receipts omit the tax-ID line unless `ORG_EIN` is set — printing a placeholder EIN would forge a tax document.

- **Ticket money is not donation money, and the two tables are separate on purpose.** A prepaid event seat is paid for through `create-ticket-session` — one call that books the seat *and* opens Checkout, because a hold with no session attached is a seat nobody can pay for — and the amount is read from `events.fee` inside the function, never taken from the request body. The payment is recorded on the `rsvps` row (`payment_status`, `amount_cents`, `stripe_session_id`, `paid_at`), not in `donations`: a ticket buys admission, which is exactly the "goods or services" that makes a payment non-deductible under IRS Pub. 1771, so it must never reach a receipt stating that nothing was given in return. The confirmation email is the same `send-rsvp-confirmation` a free RSVP gets, with a payment block added, and it is sent by the trigger on the update to `paid` rather than from the webhook — one copy of the bilingual templates. **Stripe is the only way this site takes money for a seat**: there is no way for staff to record a fee taken in person. That was built and removed before it was ever used — the organisation does not want two kinds of money in one table, and `payment_status = 'paid'` is worth more as a narrow claim (Stripe took it) than a broad one. An event either charges through this site or stays out of the transaction entirely. Stripe returns to `?ticket=success&session_id=…`, which `App.tsx` reads and routes to the **events** tab, where `TicketReturn` polls `ticket-status` instead of believing the query string.

- **Three build-time feature flags gate promises the backend cannot yet keep** — `src/lib/features.ts` reads `VITE_DONATIONS_ENABLED`, `VITE_EMAIL_ENABLED` and `VITE_TICKETS_ENABLED`. With donations off, `DonationWidget` shows a contact address instead of a button, and `RSVPModal` skips its step-2 donation ask entirely; with email off, the RSVP confirmation screen does not claim a message was sent (`successMessageNoEmail`). Neither flag is a stub to be removed — a donate button that always errors, or a "check your inbox" for mail that was never sent, is worse for a nonprofit than an honest "not yet". With tickets off, no event can be marked prepaid from the admin panel and one somehow already marked shows the contact address rather than a payment button — so the flag being off is exactly the behaviour the site had before tickets existed. Flip them only once Stripe/`create-checkout-session` and `RESEND_API_KEY` + the `rsvps` trigger actually exist (and, for tickets, `create-ticket-session`/`ticket-status` deployed, a `stripe-webhook` build that knows `kind: 'event_ticket'`, and the tickets migration applied — see `docs/paid-events.md`), and set them in the GitHub Actions build environment too or production stays off. `rsvpDonationEnabled` in the same file is a fourth gate but not an env flag: it is a plain `false` constant because the step it guards has never been wired to Checkout, and an env switch would invite somebody to turn it on without doing that.

- **Code splitting is deliberate on both axes.** `App.tsx` `lazy()`-loads `AdminPanel`, `VolunteerPortal` and `CertificateVerify` — three bundles a visitor who only reads the home page never fetches — and `MarkdownDocument` lazy-loads `react-markdown` the same way. `manualChunks` in `vite.config.ts` splits `vendor-react`, `vendor-supabase` and `vendor-i18n` out of the entry chunk because the social-post workflow republishes the site on a schedule, and without it a returning visitor re-downloads React because a caption changed. `lucide-react` is excluded on purpose: its named imports tree-shake to the ~70 icons used, and forcing it into a chunk would pull in the rest. Converting any of these to a static import silently undoes it — nothing fails.

- **Images** come from two places, resolved by `resolveImage()` in `src/lib/api/images.ts`: photos bundled in `src/assets/*.webp` are content-hashed by Vite, so the database stores an `image_key` naming an entry in the `IMAGES` registry; admin uploads go to the `media` Storage bucket and store an absolute `image_url`, which wins when both are present.

- **`src/data/mockData.ts` is now only the `IMAGES` registry** despite its name — events, gallery, shifts and the volunteer profile moved to Postgres. `src/data/socialPosts.ts` is still genuinely mock data. The other two modules in that directory are not mock data at all and are each a single source of truth: `orgLinks.ts` holds the real public URLs and the postal address in parts (the footer joins them, `seo.ts` feeds them to `PostalAddress` structured data, so the two cannot drift) — note the handles genuinely differ per platform, `paowtx` on Instagram/X but `pawtx` on Facebook/YouTube, so "fixing" one to match produces a 404. `volunteerRoles.ts` holds the six role values fixed by a CHECK constraint on `shifts.role` together with their Spanish labels, which is what stops an admin typing `role_es` (free text in the database) three different ways.

- **Live social feed** — `SocialMediaFeed` fetches `public/social-posts.json` on mount; when it is missing or empty the section shows an honest "not connected yet" notice, never sample posts (`INITIAL_SOCIAL_POSTS` is deliberately empty). Post images are **not** Meta's URLs — those are signed CDN links that expire within days — but WebP copies the fetcher stores in `public/social-media/<post id>.webp`, written once and never re-encoded, pruned when a post drops off the feed; the JSON carries a root-relative path and the component prefixes `BASE_URL`. When one platform's fetch fails, the script keeps that platform's previous posts and exits non-zero; the workflow still commits (`if: !cancelled()`), so a revoked token emails the owner without emptying the live feed. That JSON is generated by `scripts/fetch-social-posts.mjs` via Meta Graph API calls, run on a schedule by `.github/workflows/fetch-social.yml` (needs `FB_PAGE_ACCESS_TOKEN`/`FB_PAGE_ID`/`IG_USER_ID` repo secrets — see README). The workflow commits the refreshed JSON to `main`, which triggers `deploy.yml` to rebuild/republish — this is still a fully static site, no live backend. Relative post ages (`formatRelativeTime` in `src/lib/relativeTime.ts`) are computed at render time from `publishedAt` rather than trusting baked `publishedAtRelative` strings, since the JSON only refreshes every few hours.

- **Adding a bundled image:** drop the source `.jpg` in `src/assets/`, run `npm run optimize:images` to convert it to WebP, delete the `.jpg`, then `import` the `.webp` in `mockData.ts` and assign it a key in `IMAGES`. Reference it from a database row by putting that key in `image_key`. This requires `src/vite-env.d.ts` (`/// <reference types="vite/client" />`) — without it, `tsc` fails on image imports.

- **Image pipeline** — `scripts/optimize-images.mjs` (sharp, a devDependency) resizes `src/assets/*.jpg` to a 1000px long edge (1600 for the hero, 512 for the logo) and re-encodes to WebP, which took the bundled photos from 7.5 MB to 2.5 MB. Straight-from-camera photos are far larger than anything the UI renders, so never commit one unprocessed. That script only touches build-time assets — admin uploads are resized in the browser by `resizeImageFile()` in `src/lib/api/admin.ts` (canvas → WebP, 1600px long edge) before they reach Storage, for the same reason. Only the hero is eager (`fetchPriority="high"`); every other `<img>` is `loading="lazy"`, which keeps the initial home-page load to ~3 images instead of ~25.

- **Dates** — the database stores real `timestamptz`; the human labels (`event.date`, `event.time`, `gallery.date`) are derived per-language in `src/lib/formatEventDate.ts` and pinned to `America/Chicago`, so "6:30 PM" always means 6:30 PM at the venue. `wallClockToInstant` / `instantToWallClock` convert for the admin panel's `datetime-local` inputs and handle DST correctly. Do not reintroduce human date strings in stored data.

- **i18n (bilingual EN/ES)** — `src/i18n/config.ts` holds **all** translations inline in one `resources` object. Two patterns coexist: (1) keyed strings via `useTranslation()` `t('...')`; (2) inline `isEs`/`language === 'es'` ternaries reading parallel data fields (`titleEs`, `descriptionEs`, `captionEs`, `roleEs`). `BrochureShowcase` is fully pattern (2). The store's `setLanguage` calls `i18n.changeLanguage` and sets `language`; components read `language` from the store, not just from i18next. Any new user-facing string must be handled in both languages.

- **Styling** — Tailwind v4 via the `@tailwindcss/vite` plugin. **There is no `tailwind.config.js`**: the theme (brand colors, fonts, radii) is declared in `src/index.css` inside `@theme`. Brand palette: terracotta `#A64D32`, olive `#5B6346`, parchment `#FDFBF7`, aged-paper `#F4F1ED`, graphite `#2A2A2A`; fonts Playfair Display (serif/headings) + Inter (sans). The custom classes `animate-fadeIn`, `animate-scaleUp`, `animate-shimmer`, and `scrollbar-none`/`no-scrollbar` are **hand-written plain CSS** at the bottom of `index.css` — they are NOT Tailwind built-ins. If you use a new `animate-*` class, define its `@keyframes` in `index.css` or it silently does nothing.

- **Head metadata is static, and has to be.** No link-preview crawler (Facebook, X, WhatsApp, LinkedIn, iMessage, Slack) runs JavaScript, so anything the bundle adds to `<head>` is invisible to them. `index.html` therefore carries the whole crawler-facing set — description, Open Graph, Twitter card, canonical, icons, and the `Organization` JSON-LD — with `%TOKEN%` placeholders filled in at build time by the `pawtxSeo()` plugin in `vite.config.ts` from **`src/lib/seo.ts`**, which is the single source of truth (and where `CANONICAL_URL` lives; changing domain means editing it and `SITE_PATH`, which is also the Vite `base`). The same plugin emits `robots.txt` and `sitemap.xml`; `site.webmanifest` cannot be emitted that way because `index.html` links to it and Vite resolves link hrefs against `public/` before anything is emitted. Its icon paths are relative on purpose so they survive the Pages sub-path. Never write a literal `</head>` inside an `index.html` comment — Vite injects the bundle before the first one it finds and will bury the whole app in the comment. The same plugin also injects the hero `<link rel="preload">`, matching the content-hashed asset with a regex on `hero-parade-*.webp`: the hero is the LCP element but lives inside `Hero.tsx`, so the preload scanner cannot see it until the bundle has executed. Renaming that source file makes the regex miss and the preload silently disappear — no build error, just a slower first paint.

- **Do not render head tags from React.** `react-helmet-async` was removed: on React 19 it hoists tags natively rather than adopting the ones already in the document, so every `<meta>` it repeated from `index.html` appeared in the page twice. `App.tsx` sets `document.title` and `document.documentElement.lang` in a plain effect instead. Per-tab descriptions and `og:` tags were dropped rather than fixed — with no router the whole site is one URL, so there is nothing for a second description to be indexed as, and a shared link always resolves to the home page.

- **Scroll reveal** — wrap sections in `AnimatedSection` (IntersectionObserver toggles transition classes on visibility). Used pervasively on the home page.

- **Modals** are mounted once at the `App` root and toggled by store flags: `RSVPModal` (`selectedEventForRsvp`), `SearchModal` (`isSearchOpen`, global ⌘K/Ctrl+K listener; indexes events + gallery + shifts), `ContactModal` (local `App` state). Gallery uses a lightbox driven by `lightboxItemIndex` in the store.

- **Error handling** — the `ErrorBoundary` class component wraps both the root (`main.tsx`) and the main content region (`App.tsx`).

- **The social feed is read-only, on purpose.** Cards show the like and comment counts Meta reported at the last fetch and link out to the post; there is no like, comment, bookmark or refresh control, and no AI summary. Those used to exist and none of them reached Meta — a like changed the count in one tab, a comment toasted "Comment posted" and went nowhere, refresh waited 700 ms and claimed to have checked the channels, and with no Gemini key (which cannot safely be in a static bundle anyway) the summary fell back to three invented bullets. Interacting with a post happens on the platform. Do not reintroduce a control the backend cannot honour.

## Conventions & gotchas

- `@/*` path alias maps to the project root (`./*`) in both `tsconfig.json` and `vite.config.ts`.
- `EventFeed`, `Gallery`, `SocialMediaFeed` and `DonationWidget` each render both as a band of the stacked home page (where `Hero` owns the h1) and as an entire tab (where nothing else can). They take `asPageTitle` and pick their heading tag via `titleTag()` in `src/components/pageTitle.ts` — the component cannot detect which context it is in, `activeTab` decides. A hardcoded `<h2>` ships a tab with no h1, which is what axe reported and what a screen-reader user navigates by.
- Both `package-lock.json` and `bun.lock` are committed. CI (`deploy.yml`) runs `npm install` (not `npm ci`), so a dependency added only through bun still resolves in CI but the two lockfiles drift — update via npm.
- Do not touch the `server.hmr` / `server.watch` logic in `vite.config.ts` — it is gated on `DISABLE_HMR` for the AI Studio agent environment.
- `2.png`-style large source photos must go through `npm run optimize:images` before bundling — a bundled photo should be ~100-200 KB, not multiple MB.
- The files in `public/` are served under fixed names on purpose — a crawler asking for `og-image.jpg` and a browser asking for the favicon both need a URL that does not change, which content-hashed `src/assets/` imports cannot give them. Regenerate with `npm run seo:assets` and commit the result; the build does not run it.
- **Never give a secret a `VITE_` prefix.** Vite inlines those into the public bundle. Only `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` belong there (both are public by design). Stripe, Resend and the service role key live in Edge Function secrets (`supabase secrets set`), and the same two `VITE_` vars must exist as GitHub Actions secrets or the deployed build has no backend.
- Auth magic links and Stripe return URLs must be listed in Supabase → Authentication → URL Configuration → Redirect URLs — `https://pawtx.org/**` and `http://localhost:3000/**` since the move off the GitHub Pages sub-path. `getSiteUrl()` in `supabaseClient.ts` derives the address from `import.meta.env.BASE_URL`; a mismatch fails silently at click time, because Supabase substitutes the project's Site URL rather than returning an error.
- After changing a migration, run `npm run db:types` so `src/lib/database.types.ts` matches. It is currently hand-written and will drift otherwise.
- **The local stack cannot reach any table through PostgREST or an Edge Function until you grant it.** On the hosted project, every table created in `public` is granted to `anon`, `authenticated` and `service_role` by a default privilege owned by `supabase_admin` — which is the whole reason the `revoke` statements in the migrations make sense, and why revoking table-wide UPDATE is what keeps an admin out of `reserved_spots`. Locally the migrations run as `postgres`, whose default privilege gives those roles only `TRUNCATE/REFERENCES/TRIGGER`, so after `npm run db:reset` the site loads no events and every Edge Function answers "permission denied". It is not a missing migration: `donation-status`, which is untouched and works in production, fails identically. `supabase/tests/README.md` has the two `grant` lines to paste; do not "fix" this by adding them to a migration, because the hosted project does not need them and the explicit grants would then have to be kept in step with every future revoke by hand.
- `.gitattributes` pins `*.sql` to LF in the working tree, and has to. `supabase/setup/00_full_setup.sql` is compared byte for byte against what `scripts/generate-setup-bundle.mjs` builds, and the generator joins its own header and separator lines with a bare LF while copying the migration bodies through verbatim — so a CRLF checkout, which is what `core.autocrlf=true` gives every Windows clone, fails `npm run setup:check` even when nothing has drifted and leaves the bundle permanently `M` in `git status`. A check that cries wolf is one people stop reading, and this is the check standing between whoever installs from the dashboard and a stale schema.
